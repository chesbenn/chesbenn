# 08. Контроль поставщиков каналов и аплинков (SLA)

**Коротко:** платформа следит за качеством каналов, которые провайдер сам покупает (интернет-транзит, аренда волокна, каналы до удалённых узлов), сравнивает с договорами и автоматически собирает доказательства для претензий и возврата денег. Плюс — помогает выбрать, у кого и сколько полосы покупать.

---

## Проблема
- Малый провайдер платит аплинкам большие деньги, но почти никогда не требует компенсаций за простои и деградацию — нет доказательной базы, некогда.
- Договоры, сроки, цены, SLA хранятся в папках; продление «проспали» — переплата.
- Перегрузка аплинка в часы пик видна только по жалобам абонентов.
- Нет понимания, выгодно ли добавить второго аплинка, точку обмена трафиком (IX) или кэш (Google GGC, Яндекс, VK).

## Что делает
1. **Реестр договоров с поставщиками:** что покупаем (транзит, L2-канал, волокно, IP), полоса, цена, SLA (доступность, время восстановления, потери, задержка), сроки, контакты, порядок претензий.
2. **Измеряет каждый канал:** доступность (ping/BFD/BGP-сессии), задержка, потери, загрузка 95-го перцентиля, BGP-флапы.
3. **Фиксирует нарушения SLA** с доказательствами (графики, логи BGP, тикеты к поставщику).
4. **Считает положенную компенсацию** по формуле из договора.
5. **Готовит претензию** (письмо + приложения) и отслеживает её до получения денег.
6. **Следит за сроками:** продление, пересмотр цен, «потолок» 95-перцентиля для расчёта.
7. **Аналитика закупки:** загрузка в пиках, прогноз роста, стоимость Мбит/с у разных поставщиков, какой трафик можно увести на IX и кэши.
8. **Связь с абонентами:** если деградация аплинка — автоматическое объяснение абонентам и статус-страница.

## Кто пользуется
| Роль | Что делает |
|---|---|
| Сетевой инженер | Видит качество каналов, причины деградации |
| Руководитель / финансист | Договоры, расходы, претензии, решения о закупке |
| Юрист | Претензии и переписка |

## Как работает
```
Реестр договоров (ручной ввод + скан договора → ИИ извлекает ключевые условия)
  → привязка договора к интерфейсам/BGP-сессиям в графе (uplink-узлы)

Измерение
  → SNMP: загрузка интерфейсов каждые 1 мин → ClickHouse
  → активные пробы: ping/TWAMP до шлюза поставщика и до 3 внешних точек каждые 10 с
  → BGP: состояние сессий (SNMP BGP4-MIB или BMP), флапы, число префиксов
  → syslog маршрутизаторов

Нарушения
  → правило SLA из договора → детектор:
        доступность < X% за месяц, простой > N мин, потери > P% в течение T, и т.п.
  → sla_violation с интервалом, метриками, графиками (PNG), логами

Претензии
  → ежемесячно: расчёт компенсации по формуле договора
  → черновик претензии (шаблон + LLM для текста) → проверка юристом → отправка
  → статус: отправлена → признана → зачтена в счёте / отклонена

Закупка
  → отчёт: 95-перцентиль по месяцам, прогноз на 6 мес (линейный + сезонность),
    топ-ASN назначения трафика (по NetFlow, если есть) → что дешевле через IX/кэш
```

## Модель данных
```sql
CREATE TABLE supplier_contract (
  id            BIGSERIAL PRIMARY KEY,
  supplier      TEXT NOT NULL,
  service_kind  TEXT NOT NULL,           -- transit, l2_channel, dark_fiber, ip_lease, colocation
  capacity_mbps INT,
  price_month   NUMERIC(12,2),
  billing_model TEXT,                    -- flat, 95th_percentile, commit_burst
  commit_mbps   INT,
  sla           JSONB,                   -- {"availability": 99.9, "mttr_h": 4, "loss_pct": 0.5, ...}
  compensation  JSONB,                   -- формула: [{"below": 99.9, "credit_pct": 10}, ...]
  starts_on     DATE,
  ends_on       DATE,
  notice_days   INT,                     -- срок уведомления о расторжении
  claim_procedure TEXT,
  document_ids  TEXT[],
  uplink_node_ids BIGINT[]               -- интерфейсы/сессии в графе
);

CREATE TABLE sla_violation (
  id           BIGSERIAL PRIMARY KEY,
  contract_id  BIGINT REFERENCES supplier_contract(id),
  kind         TEXT NOT NULL,            -- down, loss, latency, bgp_flap, capacity
  started_at   TIMESTAMPTZ NOT NULL,
  ended_at     TIMESTAMPTZ,
  metrics      JSONB,
  evidence_ids TEXT[],                   -- графики, выгрузки логов
  supplier_ticket TEXT
);

CREATE TABLE supplier_claim (
  id           BIGSERIAL PRIMARY KEY,
  contract_id  BIGINT REFERENCES supplier_contract(id),
  period       DATE NOT NULL,            -- месяц
  violations   BIGINT[],
  amount_rub   NUMERIC(12,2),
  status       TEXT NOT NULL,            -- draft, sent, accepted, credited, rejected
  letter_id    TEXT,
  sent_at      TIMESTAMPTZ, resolved_at TIMESTAMPTZ
);
```

## Правила
- Простои считаются по данным минимум двух независимых проб (защита от ложных срабатываний собственного оборудования).
- Простой, вызванный нашими работами (модуль 07) или нашей аварией, исключается автоматически.
- Напоминание о продлении — за `notice_days + 30` дней.

## Интерфейсы
- **Панель «Аплинки»:** каждый канал — доступность за месяц, загрузка, нарушения, стоимость Мбит/с.
- **Претензии:** список, суммы, статусы, кнопка «сформировать».
- **Календарь договоров:** продления, повышения цен.
- **Отчёт закупки:** «через 4 месяца пик достигнет 85% — нужно расширение; IX сэкономит ~X ₽/мес».

## Интеграции
SNMP/BGP маршрутизаторов, активные пробы (контейнер `prober`), NetFlow/IPFIX (если есть), `files`, `llm-gateway` (извлечение условий из договоров, текст претензий), модуль 07, статус-страница.

## Метрики
- Сумма компенсаций, полученных от поставщиков в год.
- Предотвращённые автопродления невыгодных договоров.
- Время, когда аплинк был загружен > 90% (снижение).
- Стоимость Мбит/с (снижение).

## Риски
- Формулировки SLA в договорах размыты — ИИ-извлечение проверяет человек.
- Поставщик может оспаривать собственные измерения провайдера — сохранять сырые данные и тикеты к поставщику.

## MVP (2 недели)
Реестр договоров + доступность и загрузка аплинков по SNMP/ping + месячный отчёт нарушений по SLA. Претензии и аналитика закупки — вторым шагом.

## Как проверить
1. Симулятор роняет аплинк на 47 минут → нарушение SLA с графиком, расчёт компенсации по договору.
2. Падение во время наших плановых работ → нарушение не засчитано.
3. Договор, истекающий через 50 дней с notice 30 → напоминание.

## Зависимости
`graph` (аплинки), `telemetry`, коннектор маршрутизаторов, `prober`, `files`, `llm-gateway`, модуль 07.
