# 02. Поиск абонентов с проблемами до того, как они позвонят

**Коротко:** платформа каждые несколько минут проверяет каждого абонента по данным сети — сигнал ONU, ошибки на порту, обрывы сессий, скорость относительно тарифа, загрузку узла, состояние роутера — и сама находит тех, у кого интернет работает плохо. Абонент ничего не делает и никуда не звонит: провайдер видит проблему первым и чинит её сам (удалённо или выездом).

---

## Проблема
- Большинство абонентов с плохим интернетом **не звонят**, а молча уходят к конкуренту.
- Провайдер видит только полные аварии («узел упал»), но не деградацию у отдельных абонентов: сигнал медленно падает, сессия рвётся 20 раз в день, порт сыплет ошибками, роутер перезагружается.
- Поддержка узнаёт о проблеме от раздражённого абонента и начинает диагностику с нуля.

## Что делает
1. **Оценка здоровья каждого абонента** (0–100) каждые 5–15 минут, только по данным сети и биллинга.
2. **Находит конкретные причины:** «оптический сигнал −27,8 дБм и падает 0,3 дБ в неделю», «47 обрывов PPPoE за сутки», «CRC-ошибки на порту коммутатора», «упирается в тариф каждый вечер», «аплинк узла загружен на 95% с 20:00 до 23:00», «роутер перезагружался 6 раз (TR-069)».
3. **Различает уровень проблемы:** у одного абонента (его линия/роутер), у группы (сплиттер/порт/коммутатор), у всего узла (аплинк).
4. **Сам выбирает действие:**
   - удалённое — перезапуск сессии, сброс порта, перезагрузка ONU/роутера в ночное время, смена канала Wi-Fi через ACS;
   - выезд — заявка монтажнику с готовым диагнозом («чистить коннектор в щитке подъезда 2»);
   - инженеру — проблема узла/аплинка.
5. **Проверяет результат** после действия: стало ли лучше.
6. **Показывает список «кто страдает сейчас»** в NOC и поддержке, отсортированный по тяжести и стоимости абонента.
7. **Передаёт информацию в расчёт стоимости аварий (10) и прогноз оттока.**

## Кто пользуется
| Роль | Что видит / делает |
|---|---|
| NOC-инженер | Список проблемных абонентов и групп, причины, кнопки удалённых действий |
| Диспетчер | Готовые заявки на выезд с диагнозом |
| Оператор поддержки | При звонке абонента — уже известная проблема и что с ней делается |
| Руководитель | Сколько абонентов в «красной зоне», динамика, сколько исправлено без звонков |

Абонент в процессе не участвует.

## Как работает
```
Сбор (каждые 5–15 мин, всё уже есть у провайдера)
  RADIUS accounting   → сессии: обрывы, длительность, причины завершения
  OLT (SNMP)          → Rx/Tx ONU, температура, ошибки, перерегистрации
  Коммутаторы (SNMP)  → статус порта, скорость линка, CRC/ошибки, флапы
  BRAS / шейпер       → трафик абонента, упор в тариф (доля времени на полке)
  ACS (TR-069), опц.  → перезагрузки роутера, Wi-Fi-канал, загрузка CPU
  Узлы (telemetry)    → загрузка аплинка в часы пик
  Биллинг             → тариф (скорость), статус, давность подключения, ценность

Оценка
  → для каждого абонента набор признаков за 24 ч и 7 дней
  → штрафные баллы по правилам (таблица ниже) → health = 100 − Σ штрафов
  → причины = признаки, давшие штраф, понятным языком

Группировка (graph)
  → если у ≥ 30% абонентов одного сплиттера/порта/коммутатора те же признаки →
        это проблема группы → один случай на объект, а не 40 по абонентам
  → если проблема у всех за аплинком → случай "перегрузка узла"

Действие
  → правило "причина → действие" (таблица ниже)
  → удалённые действия выполняются автоматически ночью (если включено) или по кнопке
  → выезд: заявка с диагнозом, местом (щиток/подъезд) и материалами
  → через 24 ч после действия: пересчёт health → закрыть или эскалировать
```

## Правила оценки (начальные, настраиваются)
| Признак | Порог | Штраф |
|---|---|---|
| Rx ONU | хуже −27 дБм | 30 |
| Rx ONU падает | > 0,2 дБ/неделю | 15 |
| Перерегистрации ONU | > 3 за сутки | 20 |
| Обрывы сессии | > 5 за сутки | 20; > 20 — 40 |
| Ошибки CRC на порту | > 100 за час | 25 |
| Линк порта | 100 Мбит/с при тарифе > 100 | 20 |
| Упор в тариф | > 30% вечернего времени | 10 (повод предложить тариф выше — менеджеру) |
| Перегрузка аплинка узла | > 85% в пик | 15 всем за узлом |
| Перезагрузки роутера | > 2 за сутки | 15 |
| Плохой Wi-Fi-канал (ACS) | загрузка канала > 70% | 10 |

`health ≥ 80` — норма, `60–79` — внимание, `< 60` — проблема.

## Правила действий
| Причина | Действие |
|---|---|
| Низкий/падающий Rx у одного | Заявка: чистка/замена коннектора, проверка патч-корда |
| Низкий Rx у группы на сплиттере | Заявка инженеру: сплиттер/магистраль |
| Флапы и CRC на порту | Ночью: сброс порта; повтор → заявка «кабель/разъём» |
| Линк 100 Мбит/с | Заявка: перекрутить/заменить коннектор, проверить кабель |
| Частые обрывы сессии без проблем линии | Проверить роутер через ACS → перезагрузка/обновление прошивки ночью |
| Перегрузка аплинка | Инженеру + модуль 04 (ёмкость) |
| Упор в тариф | Менеджеру: предложение тарифа (звонок менеджера — по решению провайдера) |

## Модель данных
```sql
-- Сырые признаки — в ClickHouse
CREATE TABLE sub_health_raw (
  ts            DateTime,
  subscriber_id UInt64,
  rx_dbm        Nullable(Float32),
  onu_rereg     UInt16,
  session_drops UInt16,
  port_crc      UInt32,
  link_mbps     Nullable(UInt16),
  shelf_pct     Float32,           -- доля времени "на полке" тарифа
  cpe_reboots   UInt16,
  uplink_util   Float32
) ENGINE = MergeTree ORDER BY (subscriber_id, ts) TTL ts + INTERVAL 180 DAY;

-- Текущее состояние — в PostgreSQL
CREATE TABLE sub_health (
  subscriber_id BIGINT PRIMARY KEY,
  score         SMALLINT NOT NULL,
  level         TEXT NOT NULL,             -- ok, warn, bad
  reasons       JSONB NOT NULL,            -- [{"code": "rx_low", "value": -27.8, "text": "..."}]
  group_case_id BIGINT,                    -- если проблема групповая
  action        TEXT,                      -- последнее действие
  action_at     TIMESTAMPTZ,
  updated_at    TIMESTAMPTZ NOT NULL
);

CREATE TABLE health_case (
  id          BIGSERIAL PRIMARY KEY,
  scope       TEXT NOT NULL,               -- subscriber, splitter, port, switch, node
  object_id   BIGINT NOT NULL,             -- узел графа
  subscribers INT NOT NULL,
  reasons     JSONB NOT NULL,
  action      TEXT,
  task_id     BIGINT,
  status      TEXT NOT NULL,               -- open, action_taken, verifying, fixed, escalated
  opened_at   TIMESTAMPTZ DEFAULT now(),
  closed_at   TIMESTAMPTZ
);
```

## Интерфейсы
- **NOC: «Кто страдает сейчас»** — список случаев (сначала групповые), причины, число абонентов, кнопки «выполнить действие» / «создать заявку».
- **Карта:** дома и узлы окрашены по среднему health.
- **Карточка абонента** (модуль 06): health, график за 30 дней, причины.
- **Утренний отчёт руководителю:** «вчера найдено 132 проблемы, 97 исправлено удалённо, 21 заявка, 14 в работе; звонков по ним — 6».

## Интеграции
RADIUS, OLT и коммутаторы (SNMP), BRAS/шейпер, ACS (опционально), `graph`, `telemetry`, `tasks`, модули 04, 06, 10.

## Метрики успеха
- Доля проблем, найденных **до** звонка абонента (цель > 80%).
- Доля исправленных удалённо.
- Число абонентов в зоне `bad` (снижение).
- Обращения в поддержку на 100 абонентов (снижение).
- Отток среди абонентов, побывавших в `bad` (снижение).

## Риски
- Удалённые действия днём мешают абонентам — по умолчанию только ночью (02:00–05:00) и не чаще раза в сутки.
- Пороги зависят от оборудования — первые 2 недели режим «только наблюдение» для калибровки.

## MVP (2 недели)
RADIUS-обрывы + Rx ONU + ошибки портов → health → список «кто страдает» с группировкой по сплиттеру/порту. Автоматические действия — вторым шагом.

## Как проверить
1. В симуляторе у одного абонента Rx падает до −28 дБм → `bad`, причина «низкий сигнал», заявка с диагнозом.
2. У 12 из 16 ONU сплиттера падает Rx → один групповой случай на сплиттер, а не 12.
3. 30 обрывов сессии за сутки при нормальной линии → ночная перезагрузка роутера через ACS → через сутки `ok`.

## Зависимости
`graph`, `telemetry`, коннекторы RADIUS/OLT/коммутаторов/BRAS, ACS (опц.), `tasks`.
