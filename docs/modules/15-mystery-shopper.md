# 15. Автоматический «тайный покупатель»

**Коротко:** платформа регулярно сама проверяет провайдера глазами клиента: звонит на линию поддержки и замеряет ожидание, пишет в чат и бот, проходит путь «узнать цену → оставить заявку», оплачивает тестовый счёт, проверяет сайт и личный кабинет. Руководитель каждое утро знает, работает ли то, через что клиенты к нему приходят и платят.

---

## Проблема
- Отзывы абонентов: «поддержка 24/7» на деле работает 10:00–22:00, ожидание до 20 минут; заявки с сайта теряются; оплата «не проходит».
- Руководитель узнаёт о проблемах в клиентском пути из отзывов и от ушедших абонентов.
- После обновлений сайта или биллинга ломается форма заявки или оплата — никто не замечает днями.

## Что делает
1. **Звонок на линию** (по расписанию, в разное время, включая ночь): время до ответа IVR, время до оператора, работают ли пункты меню, есть ли автоответ при аварии.
2. **Сообщения в каналы:** Telegram-бот, чат на сайте, WhatsApp, VK — время первого ответа, адекватность ответа (ИИ-оценка).
3. **Путь продажи:** на сайте ввести адрес → проверить, что расчёт (модуль 04) отвечает, форма заявки отправляется, заявка появилась в системе, менеджер связался за N минут.
4. **Оплата:** тестовый платёж на служебный лицевой счёт через СБП/карту → проверка зачисления и разблокировки за N секунд → автоматический возврат.
5. **Личный кабинет / Mini App:** вход, отображение баланса, смена тарифа на тестовом аккаунте.
6. **Сайт:** доступность, скорость загрузки, сертификат, актуальность тарифов (совпадают ли с биллингом).
7. **Отчёт и тревоги:** утренняя сводка + немедленная тревога при поломке (оплата не прошла, бот молчит).
8. **Оценка операторов** (если включено): по записанным тестовым звонкам — вежливость, правильность ответа, следование скрипту.

## Кто пользуется
| Роль | Что делает |
|---|---|
| Руководитель | Утренняя сводка, тренды качества сервиса |
| Руководитель поддержки | Время ответа, качество ответов, проблемы в сменах |
| Маркетинг / продажи | Работа воронки «сайт → заявка → звонок менеджера» |
| ИТ | Тревоги о поломках оплаты, кабинета, сайта |

## Как работает
```
Планировщик (scheduler): сценарии × расписание (случайное время в заданных окнах)

Сценарий "звонок"
  → SIP-клиент (Asterisk/FreeSWITCH или облачная телефония API) звонит на номер поддержки
  → распознавание речи: фиксирует время до IVR, нажимает пункты меню, ждёт оператора
  → при ответе оператора — короткий вопрос по сценарию синтезированной речью
        ("подскажите, какие тарифы есть для частного дома?") — или сразу вежливое завершение
        (режим настраивается, чтобы не мешать операторам в часы пик)
  → запись (только при согласии/внутренней политике) → ИИ-оценка ответа

Сценарий "чат/бот"
  → служебный аккаунт пишет вопрос из набора → ждёт ответ → время и ИИ-оценка корректности

Сценарий "продажа"
  → headless-браузер (Playwright): сайт → ввод тестового адреса → расчёт → форма заявки с меткой TEST
  → проверка: заявка появилась в tasks (API) за < 1 мин; отметка "менеджер позвонил" за N мин
  → тестовая заявка автоматически закрывается

Сценарий "оплата"
  → служебный лицевой счёт с отрицательным балансом
  → платёж 10 ₽ через СБП-тестовый/реальный шлюз → ждать bill.payment.received
  → проверить разблокировку (CoA на тестовой сессии) → возврат платежа

Результаты → mystery_check → агрегаты → сводка в Telegram в 8:30 + тревоги сразу
```

## Модель данных
```sql
CREATE TABLE mystery_scenario (
  code        TEXT PRIMARY KEY,           -- call_support, chat_bot, chat_site, sales_flow, payment_sbp, cabinet
  schedule    TEXT NOT NULL,              -- cron или окна
  params      JSONB,                      -- номера, вопросы, тестовые аккаунты
  thresholds  JSONB,                      -- {"answer_sec": 120, "payment_sec": 60}
  enabled     BOOLEAN DEFAULT true
);

CREATE TABLE mystery_check (
  id          BIGSERIAL PRIMARY KEY,
  scenario    TEXT REFERENCES mystery_scenario(code),
  started_at  TIMESTAMPTZ NOT NULL,
  finished_at TIMESTAMPTZ,
  success     BOOLEAN NOT NULL,
  metrics     JSONB,                      -- {"ivr_sec": 4, "operator_sec": 312, "quality": 0.8}
  failure_step TEXT,
  artifacts   TEXT[]                      -- скриншоты, записи
);
```

## Правила
- Все тестовые сущности (заявки, платежи, аккаунты) помечены `TEST` и исключены из отчётов продаж и финансов.
- Тестовые звонки — не чаще 4 в день и не в часы аварий (не нагружать линию в кризис).
- Операторы знают, что тайные проверки существуют (честная политика); оценки используются для обучения, а не для штрафов (настраивается руководителем).
- Тревога при сбое — только после повторной неудачи через 5 минут (исключить случайности).

## Интерфейсы
- **Утренняя сводка** в Telegram: «Звонок: ответ оператора 2:40 (норма 2:00) ⚠️; Бот: 8 с ✅; Оплата СБП: 14 с ✅; Заявка с сайта: менеджер не перезвонил за 30 мин ❌».
- **Дашборд:** тренды по каждому сценарию, по часам и дням недели.
- **Разбор:** записи и скриншоты неудачных проверок.

## Интеграции
Телефония (SIP/API), распознавание и синтез речи, Playwright, бот и чаты (служебные аккаунты), биллинг (служебный счёт), платёжный шлюз, `tasks`, `notify`, `llm-gateway`.

## Метрики
- Время до ответа оператора по часам (реальное, а не из отчёта АТС).
- Доступность ключевых путей: оплата, заявка, кабинет (цель 99,5%).
- Время от поломки пути до обнаружения (цель < 30 мин).

## Риски
- Тестовые звонки отвлекают операторов — ограниченная частота, быстрое завершение.
- Тестовые платежи требуют аккуратной настройки возвратов и пометок в бухгалтерии.

## MVP (1 неделя)
Сценарии «сайт → заявка» (Playwright) и «бот отвечает» + проверка доступности сайта и кабинета + утренняя сводка. Звонки и оплата — вторым шагом.

## Как проверить
1. Включить сценарий «продажа» на демо-сайте → тестовая заявка появляется и закрывается, результат в сводке.
2. Сломать форму заявки → через ≤ 10 мин тревога «заявка не создана».
3. Тестовая оплата → зачисление и разблокировка в пределах порога.

## Зависимости
`scheduler`, `tasks`, биллинг, телефония, Playwright, `notify`, `llm-gateway`.
