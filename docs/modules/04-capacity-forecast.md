# 04. Прогноз ёмкости сети

**Коротко:** платформа сама следит, где заканчиваются ресурсы сети — порты на сплиттерах и коммутаторах, места на PON-портах и OLT, полоса аплинков, IP-адреса, мощность BRAS — и заранее говорит: «через 2 месяца на ул. Мира не будет свободных портов», «аплинк узла 5 упрётся в потолок в январе». Провайдер достраивает сеть и закупает оборудование вовремя, а не после жалоб и отказов в подключении.

---

## Проблема
- Свободные порты и ёмкость считаются вручную или не считаются: монтажник приезжает подключать — а портов нет.
- Перегрузка аплинков и PON-портов видна только по жалобам в часы пик.
- Оборудование при параллельном импорте едет 2–3 месяца — если заказывать по факту нехватки, будет поздно.
- IPv4-адреса заканчиваются незаметно.

## Что делает
1. **Учёт всех ресурсов** по данным сети (без ручного ввода):
   - порты коммутаторов (занято/свободно/неисправно);
   - PON: ONU на порту (из 64/128), порты сплиттеров (по графу), бюджет мощности;
   - OLT: свободные PON-порты, загрузка CPU/памяти;
   - аплинки: загрузка в часы пик (95-й перцентиль);
   - BRAS: число сессий, CPU, пропускная способность;
   - IP-пулы: занято/свободно, CGNAT — порты на адрес.
2. **Прогноз** на 3/6/12 месяцев по каждому ресурсу: рост числа абонентов в районе + рост трафика на абонента + сезонность.
3. **Ранние предупреждения:** «ресурс закончится через N недель», где N меньше, чем срок закупки + монтажа.
4. **Рекомендации:** что поставить и куда (сплиттер 1:8 в подъезде 3, второй аплинк 10G, новая PON-плата), примерная стоимость.
5. **Список закупки** на квартал с приоритетами (связь со складом).
6. **Перекосы:** где ёмкость простаивает (дорогие порты без абонентов) — можно перенести оборудование.

## Кто пользуется
| Роль | Что видит / делает |
|---|---|
| Технический директор | Прогнозы, рекомендации, план расширения |
| Инженер | Конкретные точки нехватки, что ставить |
| Снабжение | Список закупки с датами «заказать до» |
| Руководитель | Бюджет на расширение на квартал/год |

## Как работает
```
Сбор (каждый час; трафик — каждые 5 мин)
  graph        → все порты, сплиттеры, PON-порты, OLT, аплинки, их связи
  SNMP         → статусы портов, число ONU, загрузка интерфейсов, CPU
  RADIUS/BRAS  → сессии, пулы адресов
  биллинг      → подключения и отключения по адресам (динамика)

Текущая ёмкость
  → для каждого ресурса: всего, занято, неисправно, свободно, % заполнения

Прогноз
  → рост абонентов: тренд подключений минус отключений по дому/району за 12 мес
  → рост трафика: тренд 95-го перцентиля на абонента в пик (обычно +20–40% в год)
  → сезонность: осень/зима выше
  → дата исчерпания = когда прогноз заполнения достигнет порога (порты 90%, полоса 80%)

Предупреждение
  → запас_недель = (дата исчерпания − сегодня)
  → если запас < срок_закупки + срок_монтажа + 2 недели → рекомендация в план
  → рекомендация: тип расширения по правилам + стоимость из справочника цен
```

## Модель данных
```sql
CREATE TABLE capacity_resource (
  id            BIGSERIAL PRIMARY KEY,
  object_id     BIGINT NOT NULL REFERENCES graph_node(id),
  kind          TEXT NOT NULL,           -- switch_ports, splitter_ports, pon_onu, olt_pon_ports,
                                         -- uplink_bw, bras_sessions, ip_pool, cgnat_ports
  total         NUMERIC NOT NULL,
  used          NUMERIC NOT NULL,
  broken        NUMERIC DEFAULT 0,
  unit          TEXT NOT NULL,           -- ports, onu, mbps, sessions, ips
  threshold_pct NUMERIC DEFAULT 90,
  measured_at   TIMESTAMPTZ NOT NULL
);

CREATE TABLE capacity_forecast (
  resource_id     BIGINT REFERENCES capacity_resource(id),
  computed_on     DATE,
  exhaust_on      DATE,                  -- прогноз даты исчерпания
  weeks_left      NUMERIC,
  growth_per_month NUMERIC,
  confidence      REAL,
  PRIMARY KEY (resource_id, computed_on)
);

CREATE TABLE capacity_recommendation (
  id            BIGSERIAL PRIMARY KEY,
  resource_id   BIGINT REFERENCES capacity_resource(id),
  action        TEXT NOT NULL,           -- add_splitter, add_switch, add_pon_card, upgrade_uplink,
                                         -- add_ip_block, enable_cgnat, move_equipment
  details       JSONB,
  cost_estimate NUMERIC(12,2),
  order_by      DATE,                    -- заказать не позже
  status        TEXT NOT NULL            -- proposed, approved, ordered, installed, rejected
);
```

## Правила
- Пороги: порты/ONU — 90%; полоса — 80% от 95-го перцентиля в пик; IP — 85%; BRAS CPU — 70% в пик.
- Срок закупки по умолчанию: 10 недель для импортного оборудования, 2 недели для расходников (настраивается по позициям).
- Прогноз с низкой уверенностью (мало истории) показывается, но не попадает в автоматический план закупки.

## Интерфейсы
- **Карта ёмкости:** дома/узлы цветом по запасу (зелёный > 6 мес, жёлтый 2–6, красный < 2).
- **Таблица «Закончится скоро»:** ресурс, где, через сколько недель, что сделать, «заказать до».
- **План расширения на квартал** с суммой и кнопками «утвердить» → склад/снабжение.
- **Простаивающая ёмкость:** что можно перенести.

## Интеграции
`graph`, `telemetry`, коннекторы SNMP/OLT/BRAS/RADIUS, биллинг (динамика подключений), склад и справочник цен, модули 02 (перегрузка узлов), 08 (аплинки), 13 (новостройки).

## Метрики успеха
- Случаи «приехали подключать — нет порта» (цель → 0).
- Часы перегрузки аплинков в пик (снижение).
- Срочные закупки «по факту» (снижение).

## Риски
- Неполный граф (сплиттеры не внесены) → ёмкость сплиттеров неизвестна. Порты коммутаторов, ONU на PON-портах, аплинки и пулы считаются полностью автоматически; сплиттеры — по мере заполнения графа.

## MVP (1–2 недели)
Порты коммутаторов + ONU на PON-портах + загрузка аплинков + IP-пулы → текущее заполнение и линейный прогноз → таблица «закончится скоро».

## Как проверить
1. В симуляторе PON-порт с 58/64 ONU и ростом 2 ONU/мес → прогноз исчерпания через ~3 мес → рекомендация «новый PON-порт», «заказать до».
2. Аплинк с пиком 7,2 из 10 Гбит/с и ростом 3%/мес → предупреждение и рекомендация расширения.
3. Порт коммутатора без абонентов 6 месяцев → в списке простаивающей ёмкости.

## Зависимости
`graph`, `telemetry`, коннекторы, биллинг, склад/справочник цен.
