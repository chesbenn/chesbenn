# 11. Реестр критичных абонентов

**Коротко:** платформа знает, какие абоненты особенно важны — больницы, школы, аптеки, банкоматы, видеонаблюдение «Безопасного города», диспетчерские лифтов, домофоны, люди с медицинскими устройствами на удалённом мониторинге, VIP-клиенты. При любой аварии они видны первыми, им восстанавливают связь в первую очередь, а при плановых работах их учитывают заранее.

---

## Проблема
- В аварии на 300 абонентов теряется тот единственный, для кого связь критична (касса аптеки, камеры на перекрёстке, лифтовая диспетчерская).
- Об их важности знает только «старый инженер», в системах этого нет.
- Плановые работы проводятся, не учитывая, что за узлом — больница.
- Нарушение связи для госзаказчиков может стоить контракта и штрафов.

## Что делает
1. **Реестр:** категория критичности, причина, контактное лицо, требования (время восстановления, резервирование), договор.
2. **Автоматическое выявление кандидатов:** по названиям юрлиц (больница, поликлиника, школа, ОВД, аптека), по ОКВЭД, по тарифам (B2B с SLA), по услугам (камеры, домофоны) — с подтверждением менеджером.
3. **Подсветка в аварии:** «В инциденте 3 критичных: поликлиника №2 (категория 1), диспетчерская лифтов (2), аптека (3)».
4. **Порядок восстановления:** очередь работ по критичности; монтажник видит, что чинить первым.
5. **Проактивный звонок/сообщение** ответственному лицу за 1–5 минут после начала аварии.
6. **Учёт при плановых работах** (модуль 07) и при оценке стоимости аварий (модуль 10).
7. **Проверка резервирования:** у категории 1 должен быть второй канал/путь — платформа по графу проверяет, нет ли общей точки отказа.
8. **Отчёт для заказчика** о доступности за период.

## Категории (по умолчанию)
| Категория | Примеры | Цель восстановления | Уведомление |
|---|---|---|---|
| 1 — жизнь и безопасность | больницы, скорая, пожарные, «Безопасный город», лифтовые диспетчерские | 1–2 ч, круглосуточно | звонок + сообщение за 2 мин |
| 2 — общественно важные | школы, детсады, МФЦ, банкоматы, аптеки, ЖКХ-диспетчерские | 4 ч | сообщение за 5 мин |
| 3 — бизнес с SLA | B2B с договором SLA | по договору | по договору |
| 4 — особые абоненты | люди с медустройствами на мониторинге, VIP | 4–8 ч | сообщение |

## Как работает
```
Наполнение
  → коннектор биллинга: юрлица, ИНН, названия, тарифы, услуги
  → (опц.) обогащение по ИНН: ОКВЭД из открытых реестров
  → правила + LLM-классификация названия → кандидаты с категорией
  → менеджер подтверждает / отклоняет → critical_subscriber
  → для категорий 1–2: проверка резервирования по графу

Авария (inc.opened / inc.updated)
  → graph: downstream(объекты инцидента) ∩ critical_subscriber
  → если есть: приоритет инцидента поднимается до max(категория)
  → notify: ответственному лицу абонента и дежурному руководителю
  → tasks: порядок восстановления — сначала участки с критичными
  → карточка инцидента: блок "Критичные абоненты"

Проверка резервирования (ежесуточно)
  → для каждого критичного с двумя подключениями:
        пути до ядра (graph) → общие узлы? → "единая точка отказа: OLT-2"
```

## Модель данных
```sql
CREATE TABLE critical_subscriber (
  subscriber_id   BIGINT PRIMARY KEY REFERENCES graph_node(id),
  category        SMALLINT NOT NULL,         -- 1..4
  reason          TEXT NOT NULL,             -- hospital, school, cctv_city, lift_dispatch, sla, medical, vip
  restore_target_min INT,
  contacts        JSONB NOT NULL,            -- [{name, phone, telegram, role, hours}]
  redundancy_required BOOLEAN DEFAULT false,
  redundancy_status TEXT,                    -- ok, single_point:<node_id>, none
  confirmed_by    BIGINT,
  confirmed_at    TIMESTAMPTZ,
  review_due      DATE                       -- раз в год пересмотр
);

CREATE TABLE critical_candidate (
  subscriber_id  BIGINT PRIMARY KEY,
  suggested_category SMALLINT,
  evidence       JSONB,                      -- {"name": "ГБУЗ Поликлиника №2", "okved": "86.21"}
  status         TEXT NOT NULL               -- pending, accepted, rejected
);
```

## Правила
- Абонент категории 4 «медицинские устройства» вносится только с явного согласия абонента (персональные данные о здоровье).
- Реестр пересматривается раз в год (`review_due`), контакты проверяются тестовым сообщением.
- Если критичный абонент в инциденте, а приоритет инцидента вручную понижен — запись в журнал с причиной.

## Интерфейсы
- **Реестр:** таблица, фильтры, карта, статус резервирования.
- **Очередь кандидатов** для подтверждения.
- **Карточка инцидента:** блок критичных с кнопкой «позвонить».
- **Монтажник:** значок ⚠️ на объектах с критичными абонентами.
- **Отчёт доступности** для заказчика (PDF).

## Интеграции
Биллинг (юрлица, договоры), `graph`, `tasks`, `notify` (включая голосовой звонок), модули 07, 10; открытые реестры по ИНН (опционально).

## Метрики
- Время восстановления критичных vs цели по категориям.
- Доля критичных, уведомлённых в первые 5 минут.
- Число найденных «единых точек отказа» и устранённых.

## Риски
- Неполный реестр создаёт ложное чувство безопасности — ежемесячный отчёт «новые кандидаты».
- Персональные данные о здоровье — только с согласием и с ограниченным доступом.

## MVP (1 неделя)
Ручной реестр + подсветка в инциденте + уведомление контактов. Автоматические кандидаты и проверка резервирования — вторым шагом.

## Как проверить
1. Отметить поликлинику в демо-сети категорией 1 → авария на её OLT → инцидент получает максимальный приоритет, контакту ушло сообщение.
2. Создать работы (модуль 07) на этом OLT в рабочее время → требуется ручное подтверждение.
3. Поликлиника с двумя подключениями через один OLT → статус `single_point:OLT`.

## Зависимости
`graph`, `tasks`, `notify`, биллинг, модули 07 и 10.
