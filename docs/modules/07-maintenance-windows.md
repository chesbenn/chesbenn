# 07. Умное окно плановых работ

**Коротко:** инженер говорит «нужно перезагрузить OLT-3 / заменить коммутатор на ул. Мира», а система сама находит время, когда это заденет меньше всего людей (по реальному трафику), показывает, кого заденет, предупреждает абонентов, подавляет алерты на время работ и после работ проверяет, что всё вернулось.

---

## Проблема
- Плановые работы делаются «ночью, как обычно» или когда удобно инженеру — без понимания, кого и насколько это заденет.
- Абонентов не предупреждают или предупреждают всех подряд.
- Во время работ NOC засыпан алертами; после работ никто системно не проверяет, что все абоненты вернулись.
- Бизнес-клиенты с SLA узнают о работах постфактум.

## Что делает
1. **Заявка на работы:** объект (OLT, порт, коммутатор, узел, участок), что делаем, ожидаемая длительность, риск.
2. **Расчёт влияния** через граф: сколько абонентов, сколько бизнес-клиентов и критичных (модуль 11), какие услуги (интернет, ТВ, домофоны).
3. **Подбор лучшего окна** на 14 дней вперёд по историческому трафику и числу активных сессий за этим объектом.
4. **Проверка конфликтов:** другие работы в том же сегменте, аварии, праздники, большие события (матчи), отключения света.
5. **Согласование:** руководитель NOC подтверждает; для B2B — автоуведомление по SLA (обычно за 72 часа).
6. **Уведомления** абонентам за 24 ч и 1 ч, на статус-странице.
7. **Подавление алертов** на время окна.
8. **Чек-лист работ и отката** (что делать, если пошло не так).
9. **Проверка после работ:** сравнение «до/после» — сколько ONU/сессий было до и стало после; невернувшиеся → заявки.
10. **Отчёт:** фактическая длительность, затронуто, проблемы.

## Кто пользуется
| Роль | Что делает |
|---|---|
| Инженер | Создаёт заявку на работы, выполняет по чек-листу |
| Руководитель NOC | Согласует, видит календарь работ |
| Менеджер B2B | Получает список затронутых бизнес-клиентов |
| Абонент | Получает предупреждение |

## Как работает
```
Создание работ {объект, длительность, тип}
  → graph: downstream(объект) → абоненты, B2B, критичные, услуги
  → telemetry (ClickHouse): для каждого часа следующих 14 дней —
        прогноз активных сессий и трафика за объектом
        (среднее того же дня недели и часа за 8 недель, с поправкой на праздники)
  → стоимость окна = активные_сессии × вес
                   + B2B_в_рабочие_часы × большой_вес
                   + критичные × очень_большой_вес
                   + конфликт (другие работы, события) → исключить
  → топ-3 окна + рекомендация
  → согласование → создание maintenance_window
  → notify (абоненты, B2B по SLA), статус-страница
  → alert_suppression на окно (+15 мин запаса)
  → снимок "до" за 10 мин до начала: список онлайн-сессий и ONU
  → по окончании (инженер нажал "готово" или время вышло):
        снимок "после" через 10 мин
        разница → кто не вернулся → заявки / уведомление инженеру
  → отчёт
```

## Модель данных
```sql
CREATE TABLE maintenance_window (
  id             BIGSERIAL PRIMARY KEY,
  title          TEXT NOT NULL,
  object_ids     BIGINT[] NOT NULL,        -- узлы графа
  work_type      TEXT NOT NULL,            -- reboot, firmware, replace, fiber, power, config
  risk           TEXT NOT NULL,            -- low, medium, high
  duration_min   INT NOT NULL,
  candidates     JSONB,                    -- [{start, cost, sessions, b2b, critical}]
  starts_at      TIMESTAMPTZ,
  ends_at        TIMESTAMPTZ,
  status         TEXT NOT NULL,            -- draft, proposed, approved, notified, in_progress,
                                           -- verifying, done, failed, cancelled
  impact         JSONB,                    -- {subscribers, b2b, critical, services}
  checklist      JSONB,                    -- шаги и откат
  snapshot_before JSONB,
  snapshot_after JSONB,
  not_returned   BIGINT[],                 -- абоненты, не вернувшиеся после работ
  created_by     BIGINT,
  approved_by    BIGINT
);
```

## Правила
- Окна с B2B в рабочие часы (9–19) и с критичными абонентами — только с ручным подтверждением руководителя.
- Минимальный срок уведомления: абоненты — 24 ч; B2B — по договору (по умолчанию 72 ч).
- Работы высокого риска запрещены в пятницу после 15:00 и перед праздниками (настраивается).
- Если после работ не вернулись > 5% — автоматически эскалация инженеру, а не просто заявки.

## Интерфейсы
- **Мастер создания работ:** выбрать объект на карте/в дереве → указать длительность → увидеть влияние и 3 окна с графиком нагрузки.
- **Календарь работ** для NOC.
- **Экран «во время работ»:** таймер, чек-лист, текущий статус «до/после».
- **Отчёт по работам.**

## Интеграции
`graph`, `telemetry`, `notify`, статус-страница, Zabbix maintenance API, модули 01 (свет), 11 (критичные), 10 (стоимость аварий для неудачных работ).

## Метрики
- Доля работ с уведомлением абонентов (цель 100%).
- Среднее число затронутых онлайн-сессий на работы (снижение).
- Невернувшиеся после работ, найденные системой, а не по звонкам.
- Звонки во время плановых работ (снижение).

## Риски
- Прогноз нагрузки по истории неточен в праздники — учитывать календарь праздников и событий.
- Инженеры могут обходить систему «по-быстрому» — работы без окна видны как неожиданные аварии в отчёте руководителю.

## MVP (1–2 недели)
Расчёт влияния по графу + ручное время + уведомления + подавление алертов + проверка «до/после» по RADIUS-сессиям. Подбор окна по трафику — вторым шагом.

## Как проверить
1. Создать работы на OLT демо-сети на 30 мин → влияние посчитано, предложены окна в 3–5 утра.
2. Добавить B2B-клиента за этим OLT → окна в рабочее время исключены.
3. После работ 2 ONU не вернулись → 2 заявки и уведомление инженеру.

## Зависимости
`graph`, `telemetry` (ClickHouse), `notify`, `tasks`, модули 01, 10, 11.
