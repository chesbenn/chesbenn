# 06. Полная карточка абонента для сотрудников

**Коротко:** один экран, на котором сотрудник провайдера видит про абонента **всё**, ничего у него не спрашивая: договор и деньги, где и через что он подключён, что с линией прямо сейчас, что было за последние 30 дней, какие были аварии, работы, выезды, обращения и что система уже знает о проблеме. Вместо 5 программ и вопросов «назовите номер договора, перезагрузите роутер» — готовая картина за 2 секунды.

---

## Проблема
- Оператор и инженер открывают биллинг, Userside, веб-интерфейс OLT, Zabbix, RADIUS-логи — каждый раз, на каждый вопрос.
- Диагностика начинается с вопросов абоненту («горят ли лампочки?»), хотя ответ уже есть в сети.
- История абонента раскидана: аварии, выезды, смены оборудования, обращения не видны вместе.

## Что видно в карточке

### Шапка (всегда)
- ФИО/организация, договор, адрес, тариф, баланс, статус, дата подключения, категория (критичный — модуль 11).
- **Светофор состояния** (из модуля 02) и **одна строка вывода**: «Нет света в доме с 14:05», «Обрыв на сплиттере, бригада в пути, ETA 40 мин», «Линия в норме, сессия активна 3 дня», «Блокировка за долг 312 ₽».

### Блоки
| Блок | Что показывает | Откуда |
|---|---|---|
| **Подключение** | Цепочка: абонент → ONU/порт → сплиттер → PON-порт/коммутатор → OLT/узел → аплинк, с состоянием каждого звена | граф + SNMP |
| **Линия сейчас** | Rx/Tx ONU, температура, линк, ошибки, MAC за портом | OLT/коммутатор (запрос в реальном времени) |
| **Сессия** | Онлайн/оффлайн, IP, время, причина последнего обрыва, профиль скорости и соответствие тарифу | RADIUS/BRAS |
| **Роутер** | Модель, прошивка, аптайм, Wi-Fi, устройства (если есть ACS) | ACS |
| **Графики 30 дней** | Сигнал, трафик, обрывы, health | ClickHouse |
| **Лента событий** | Всё по времени: платежи, блокировки, смены тарифа, аварии, работы, выезды, замены оборудования, обращения, автоматические действия системы | все модули |
| **Активные случаи** | Авария/работы/отключение света, затрагивающие абонента; случаи модулей 02 и 05 | `tasks`, модули |
| **Оборудование** | Что числится за абонентом (аренда/собственность), серийники | склад, модуль 09 |
| **Деньги** | Баланс, начисления, платежи, компенсации, прогноз блокировки | биллинг |

### Кнопки действий (по правам роли)
Перезапустить сессию · сбросить порт · перезагрузить ONU/роутер · прогнать проверку линии · создать заявку (с автоматически заполненным диагнозом) · обещанный платёж · написать абоненту.

## Кто пользуется
| Роль | Что видит |
|---|---|
| Оператор поддержки | Шапка, вывод, сессия, лента, деньги; действия первого уровня |
| NOC-инженер | Всё + технические действия |
| Монтажник | Подключение, линия, оборудование по своей заявке |
| Менеджер / руководитель | Деньги, история, ценность абонента |

## Как работает
```
Открытие карточки (поиск по договору, ФИО, адресу, телефону, IP, MAC, serial ONU, логину)
  → gateway: права роли
  → параллельно:
        биллинг (кэш 1 мин)              → договор, тариф, баланс
        graph                             → цепочка подключения
        RADIUS / BRAS                      → текущая сессия
        OLT / коммутатор — живой запрос   → сигнал, линк, ошибки (таймаут 3 с, иначе последнее значение)
        ACS (если есть)                    → роутер
        ClickHouse                         → графики
        events/tasks                       → лента, активные случаи
  → движок "вывода": правила по приоритету
        1. активная авария/работы/отключение света на цепочке → сообщить это
        2. блокировка за долг → сообщить
        3. линия: LOS/низкий сигнал/порт down → сообщить
        4. сессии нет при живой линии → проблема роутера/авторизации
        5. всё в норме → "линия в норме", health
  → ответ интерфейсу за < 2 с (живые данные догружаются)

Действия
  → кнопка → коннектор.act() → журнал → результат в ленту
  → после действия — автоматическая повторная проверка через 60 с
```

## Модель данных
Карточка почти не хранит своих данных — она собирает их из других сервисов. Своё:

```sql
CREATE TABLE subscriber_timeline (     -- единая лента (заполняется событиями всех модулей)
  subscriber_id BIGINT NOT NULL,
  at            TIMESTAMPTZ NOT NULL,
  kind          TEXT NOT NULL,          -- payment, block, tariff, incident, maintenance, power,
                                        -- visit, device, contact, auto_action, recon, health
  title         TEXT NOT NULL,
  data          JSONB,
  source        TEXT NOT NULL
);
CREATE INDEX ON subscriber_timeline (subscriber_id, at DESC);

CREATE TABLE subscriber_search (       -- индекс поиска по всем идентификаторам
  subscriber_id BIGINT NOT NULL,
  key_kind      TEXT NOT NULL,          -- contract, phone, ip, mac, onu_serial, login, address
  key_value     TEXT NOT NULL,
  PRIMARY KEY (key_kind, key_value, subscriber_id)
);
```

## Правила
- Живые запросы к оборудованию ограничены (не чаще раза в 10 с на абонента), чтобы не нагружать OLT.
- Паспортные данные в карточке скрыты по умолчанию и раскрываются только ролям с правом и с записью в журнал.
- Каждое действие из карточки пишется в ленту абонента и в журнал аудита.

## Интерфейсы
- Веб-панель: строка поиска сверху, карточка на весь экран.
- Встраивается: в экран входящего звонка (по номеру телефона), в заявку монтажника, в инцидент (список затронутых → клик → карточка).
- Тот же API используется ИИ-агентом (через MCP) — он видит то же, что и оператор, в пределах своих прав.

## Интеграции
Биллинг, RADIUS/BRAS, OLT, коммутаторы, ACS, `graph`, `telemetry`, `tasks`, склад, модули 01, 02, 05, 07, 09, 10, 11.

## Метрики успеха
- Время до понимания причины при обращении (цель < 30 с).
- Доля обращений, закрытых первым оператором.
- Выезды без неисправности (снижение).
- Число программ, которые открывает оператор на одно обращение (цель — 1).

## Риски
- Медленные живые запросы к старым OLT — таймауты и показ последних известных значений с отметкой времени.
- Карточка полезна настолько, насколько полон граф — показывать звенья цепочки «неизвестно», а не скрывать их.

## MVP (2 недели)
Поиск + шапка + вывод + сессия RADIUS + сигнал ONU + баланс + лента из биллинга и инцидентов. Действия и роутер — вторым шагом.

## Как проверить
1. Найти абонента демо-сети по MAC → карточка за < 2 с со всеми блоками.
2. Включить в симуляторе обрыв на его сплиттере → вывод «обрыв на сплиттере, инцидент №…».
3. Нажать «перезапустить сессию» → действие в ленте и журнале, повторная проверка через 60 с.

## Зависимости
`graph`, `telemetry`, коннекторы, `tasks`, все модули, публикующие события в ленту.
