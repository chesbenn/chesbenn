# 10. Учёт стоимости аварий

**Коротко:** для каждой аварии платформа считает, сколько она реально стоила: компенсации абонентам, выезды и материалы, звонки в поддержку, штрафы по SLA, ушедшие после аварии абоненты. Руководитель видит не «было 40 аварий», а «аварии стоили 380 000 ₽, из них 60% — один старый узел», и может принимать решения о замене оборудования на цифрах.

---

## Проблема
- Аварии считаются по количеству и длительности, но не по деньгам.
- Решение «менять ли старый коммутатор/ИБП/участок» принимается интуитивно.
- Компенсации абонентам и B2B даются вручную, непоследовательно, часто только тем, кто пожаловался.
- Отток после аварий никто не связывает с конкретными авариями.

## Что делает
1. **Для каждого инцидента** считает прямые и косвенные затраты.
2. **Автоматическая компенсация абонентам** по правилам (например, перерасчёт за каждый час простоя > 4 ч) — всем затронутым, а не только позвонившим.
3. **Штрафы по SLA для B2B** — автоматически по договорам.
4. **Связь с оттоком:** абоненты, затронутые аварией и ушедшие за следующие 60 дней, учитываются как потеря (с пометкой вероятности).
5. **Рейтинг «дорогих» объектов:** какие узлы, участки, модели оборудования стоят больше всего денег.
6. **Расчёт окупаемости замены:** «замена ИБП на узле 12 стоит 45 000 ₽, аварии из-за питания там стоили 210 000 ₽ за год → окупится за 3 месяца».
7. **Бюджет надёжности:** план/факт по месяцам.

## Кто пользуется
| Роль | Что делает |
|---|---|
| Руководитель / владелец | Видит деньги и приоритеты вложений |
| Технический директор | Обосновывает замену оборудования |
| Финансист | Компенсации, резервы, бюджет |
| Абонент | Получает автоматический перерасчёт |

## Как работает
```
inc.resolved (инцидент закрыт)
  → graph: затронутые абоненты и B2B за время инцидента
  → telemetry/RADIUS: фактическая длительность простоя каждого абонента
        (по сессиям: оффлайн с - до, а не по времени инцидента)
  → затраты:
        компенсации = Σ правило(абонент, длительность)
        sla_penalties = Σ по B2B-договорам
        выезды = Σ заявки инцидента × стоимость выезда (часы × ставка + транспорт)
        материалы = списание со склада по заявкам инцидента
        поддержка = число обращений, привязанных к инциденту × стоимость обращения
        сверхурочные = часы ночных/выходных работ × коэффициент
  → компенсации → биллинг (проводки "компенсация за аварию №")
  → notify абонентам: "мы начислили X ₽ за перерыв связи"
  → через 60 дней: отток среди затронутых vs базовый отток района
        excess_churn × LTV → "потерянная выручка" (оценка)
  → outage_cost обновляется
  → агрегаты по объектам, моделям, причинам → рейтинг и окупаемость замены
```

## Данные
| Данные | Источник |
|---|---|
| Инциденты, причины, объекты | `tasks` (инциденты) |
| Затронутые абоненты и их простой | Граф + RADIUS-сессии / статусы ONU |
| Заявки, часы, материалы | `tasks`, склад |
| Обращения | Helpdesk/бот (привязка к инциденту) |
| B2B-договоры и SLA | Биллинг / CRM |
| Отток, LTV | Аналитика биллинга |
| Ставки: час монтажника, стоимость обращения | Настройки (руководитель) |

## Модель данных
```sql
CREATE TABLE outage_cost (
  incident_id     BIGINT PRIMARY KEY,
  object_ids      BIGINT[],
  cause           TEXT,                    -- power, fiber_cut, theft, hw_failure, config, upstream, unknown
  subscribers_hit INT,
  b2b_hit         INT,
  subscriber_hours NUMERIC(12,1),          -- суммарные часы простоя
  cost_compensation NUMERIC(12,2),
  cost_sla        NUMERIC(12,2),
  cost_field      NUMERIC(12,2),
  cost_materials  NUMERIC(12,2),
  cost_support    NUMERIC(12,2),
  cost_overtime   NUMERIC(12,2),
  cost_churn_est  NUMERIC(12,2),           -- считается через 60 дней
  total           NUMERIC(12,2) GENERATED ALWAYS AS (
                    coalesce(cost_compensation,0)+coalesce(cost_sla,0)+coalesce(cost_field,0)
                   +coalesce(cost_materials,0)+coalesce(cost_support,0)+coalesce(cost_overtime,0)
                   +coalesce(cost_churn_est,0)) STORED,
  calculated_at   TIMESTAMPTZ
);

CREATE TABLE compensation_rule (
  id           BIGSERIAL PRIMARY KEY,
  segment      TEXT NOT NULL,              -- residential, business, all
  min_hours    NUMERIC(5,1) NOT NULL,      -- от какой длительности
  formula      TEXT NOT NULL,              -- daily_fee_x_days | fixed | pct_month
  value        NUMERIC(10,2),
  exclude_causes TEXT[],                   -- например power (не наша вина) — по политике
  active       BOOLEAN DEFAULT true
);
```

## Правила
- Простой абонента считается по его фактическим данным (сессия/ONU), а не по времени инцидента — компенсация честная.
- Причины «нет света у абонента» по умолчанию не компенсируются (модуль 01), но это настраивается.
- Отток считается как превышение над нормой района (иначе завышается).
- Стоимость обращения по умолчанию = зарплата операторов / число обращений за месяц (пересчитывается ежемесячно).

## Интерфейсы
- **Карточка инцидента:** блок «Стоимость» с разбивкой.
- **Дашборд руководителя:** стоимость аварий по месяцам, топ-10 объектов, топ причин, план/факт.
- **Калькулятор замены:** выбрать объект → затраты за 12 мес → стоимость замены → срок окупаемости.
- **Абонент:** сообщение о перерасчёте, строка в истории платежей.

## Интеграции
`tasks`, `graph`, RADIUS/телеметрия, биллинг (проводки компенсаций), склад, helpdesk, B2B-договоры, модули 01, 03, 07, 08.

## Метрики
- Доля компенсаций, начисленных автоматически (цель > 95%).
- Стоимость аварий на абонента в месяц (снижение).
- Принятые решения о замене на основании расчёта и их фактическая окупаемость.

## Риски
- Неполная привязка обращений и заявок к инцидентам занижает стоимость — бот и оператор привязывают обращения к активному инциденту автоматически.
- Автокомпенсация увеличивает расходы — зато снижает звонки и отток; правила настраиваются, есть режим «рассчитать, но не начислять».

## MVP (2 недели)
Расчёт затронутых абонентов и абонент-часов по инциденту + выезды и материалы + отчёт «топ дорогих объектов». Автокомпенсации и отток — вторым шагом.

## Как проверить
1. Симулятор: обрыв на 6 ч, 80 абонентов, 2 выезда → расчёт всех статей, 80 компенсаций по правилу > 4 ч.
2. Абонент, который был оффлайн только 1 ч из 6 (вернулся на резерве) → компенсация не начислена.
3. Через 60 дней симуляции — оценка оттока появилась в стоимости.

## Зависимости
`tasks`, `graph`, телеметрия/RADIUS, биллинг, склад, модули 01, 07, 11.
