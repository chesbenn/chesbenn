# 16. Контроль условий договора: перепродажа и «расшаривание» подключения

**Коротко:** платформа обнаруживает случаи, когда одно домашнее подключение раздаётся на несколько квартир или превращено в «мини-провайдера» (кабель к соседям, общий Wi-Fi на подъезд, перепродажа в общежитии или офисном центре). Вместо блокировок она предлагает таким абонентам законный вариант — тариф «для нескольких квартир» или бизнес-тариф. Цель — вернуть недополученную выручку и снизить перегрузку сети, не испортив отношения.

---

## Проблема
- Один абонент тянет кабель или раздаёт Wi-Fi на 3–10 квартир и берёт с соседей деньги; провайдер теряет выручку, а сеть перегружена «домашним» тарифом.
- В общежитиях, гостиницах, офисных центрах «домашний» тариф используют как коммерческий.
- Провайдер обычно не замечает этого вообще или замечает по жалобам соседей на скорость.

## Что делает
1. **Выявляет признаки** нескольких домохозяйств за одним подключением (без анализа содержимого трафика):
   - много одновременно активных устройств «за роутером» (оценка по TTL и IP ID в заголовках, числу параллельных TLS-сессий к разным облачным аккаунтам — только агрегаты);
   - постоянная загрузка канала в нерабочие часы на уровне бизнеса;
   - несколько MAC-адресов роутеров за одним портом/ONU (вторая точка NAT);
   - в одном подъезде мало абонентов при высокой плотности потребления у одного;
   - тариф физлица у адреса, который в реестрах числится коммерческим объектом (гостиница, общежитие, офис).
2. **Оценивает вероятность** и **не принимает решений автоматически.**
3. **Предлагает менеджеру действие:** информационное письмо, предложение «семейного/многоквартирного» тарифа, бизнес-тарифа, отдельных подключений соседям со скидкой.
4. **Продающий подход:** соседям за этим подключением (если удалось определить подъезд) — адресная акция «подключитесь напрямую со скидкой».
5. **Учитывает договор:** работает только в тех пределах, которые разрешает публичная оферта провайдера (запрет коммерческой перепродажи — обычное условие).

## Кто пользуется
| Роль | Что делает |
|---|---|
| Менеджер по работе с абонентами | Разбирает случаи, связывается с абонентом |
| Маркетинг | Акции для соседей |
| Руководитель | Объём недополученной выручки и возвращённой |
| Юрист | Проверяет соответствие оферте и закону |

## Как работает
```
Сбор агрегатов (без содержимого трафика, без DPI-контента)
  → телеметрия BRAS/шейпера (eBPF-сенсор, модуль F1 из отчёта):
        для каждого абонента — число различных значений начального TTL (64/128) и
        "второго" NAT (TTL−1 и TTL−2), оценка числа устройств по распределению IP ID,
        число одновременных потоков, загрузка по часам
  → OLT/коммутатор: число MAC за портом/ONU
  → граф: тип здания, плотность подключений в подъезде
  → внешние реестры (опц.): адрес = гостиница/общежитие/офис

Оценка (еженедельно)
  → признаки за 14 дней → score 0..1
  → score ≥ 0.7 и устойчиво 2 недели → resale_case (status=new)

Разбор
  → менеджер видит признаки (понятным языком), историю абонента, тариф
  → выбор действия: письмо / предложение тарифа / акция соседям / закрыть (ложный)
  → результат фиксируется → обучение порогов
```

## Модель данных
```sql
CREATE TABLE resale_signal_weekly (
  subscriber_id  BIGINT,
  week           DATE,
  devices_est    REAL,                     -- оценка числа устройств
  nat_layers     SMALLINT,                 -- 1 = обычный роутер, 2+ = каскад NAT
  macs_behind    SMALLINT,
  night_util_pct REAL,                     -- средняя загрузка 01:00–06:00 от тарифа
  peak_util_pct  REAL,
  building_kind  TEXT,                     -- residential, dormitory, hotel, office, unknown
  PRIMARY KEY (subscriber_id, week)
);

CREATE TABLE resale_case (
  id            BIGSERIAL PRIMARY KEY,
  subscriber_id BIGINT NOT NULL,
  score         REAL NOT NULL,
  explanation   JSONB NOT NULL,            -- [{"signal": "devices_est", "value": 38, "norm": 12}]
  status        TEXT NOT NULL,             -- new, contacted, offer_accepted, offer_declined,
                                           -- false_positive, closed
  action        TEXT,                      -- letter, family_tariff, business_tariff, neighbor_promo
  revenue_delta NUMERIC(10,2),             -- изменение выручки после разбора
  handled_by    BIGINT,
  created_at    TIMESTAMPTZ DEFAULT now()
);
```

## Правила
- **Никаких автоматических блокировок и ограничений** по результатам модуля — только задача человеку.
- Используются только агрегированные технические признаки заголовков и объёмов; содержимое трафика и посещаемые сайты не анализируются и не хранятся.
- Многодетные семьи и «умные дома» дают много устройств — порог устройств сам по себе не основание; нужны минимум 2 независимых признака.
- Коммуникация с абонентом — вежливая, с выгодным предложением, без обвинений.
- Перед запуском — согласование с юристом: оферта, 152-ФЗ, закон «О связи» (тайна связи), внутренняя политика.

## Интерфейсы
- **Очередь случаев:** абонент, оценка, признаки в понятном виде («≈ 38 устройств при норме 8–15», «2 уровня NAT», «высокая загрузка ночью»).
- **Шаблоны писем и предложений.**
- **Отчёт:** найдено, подтверждено, ложных, возвращено выручки.

## Интеграции
eBPF-сенсор QoE/шейпер (агрегаты TTL/IP ID/потоков), OLT/коммутаторы (MAC за портом), `graph`, биллинг (тарифы, предложения), `notify`, маркетинг-модуль (акции для соседей).

## Метрики
- Доля подтверждённых случаев среди найденных (точность, цель > 70%).
- Возвращённая выручка в месяц.
- Отток среди абонентов, с которыми связались (не должен расти).

## Риски
- Ложные срабатывания портят отношения — только ручной разбор и мягкая коммуникация.
- Юридические ограничения в разных странах — модуль выключен по умолчанию, включается после юридической проверки.
- Оценка числа устройств по TTL/IP ID неточна при современных ОС (рандомизация IP ID) — использовать как один из признаков, не как доказательство.

## MVP (2 недели)
Признаки, которые уже есть без новых сенсоров: число MAC за портом/ONU, ночная загрузка, тип здания + очередь случаев для менеджера. TTL/IP ID-оценки — вторым шагом вместе с eBPF-сенсором.

## Как проверить
1. Симулятор: абонент с 2 роутерами за ONU и ночной загрузкой 70% две недели → случай со score ≥ 0,7 и понятным объяснением.
2. Абонент с 30 устройствами, но одним роутером и обычной загрузкой → случая нет.
3. Менеджер отмечает «ложный» → признаки этого абонента исключаются на 90 дней.

## Зависимости
Телеметрия BRAS/шейпера, коннекторы OLT/коммутаторов, `graph`, биллинг, `notify`, юридическое согласование.
