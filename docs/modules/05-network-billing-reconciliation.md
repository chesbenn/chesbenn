# 05. Автосверка сети и биллинга

**Коротко:** платформа каждый час сравнивает то, что есть в биллинге, с тем, что реально происходит в сети, и находит расхождения: кто пользуется интернетом без договора или с долгом, у кого скорость выше оплаченной, какие ONU и порты работают «ни на кого», какие договоры числятся активными, а в сети их нет. Все данные провайдер уже имеет — система только сводит их вместе.

---

## Проблема
- Биллинг, RADIUS, OLT, коммутаторы и шейпер живут отдельно, и со временем расходятся.
- Типичные потери: тестовые и «временные» подключения, которые забыли отключить; абоненты с долгом, у которых блокировка не сработала; неправильный профиль скорости; ONU, оставшиеся после расторжения; самовольные подключения в подъездах.
- Обратная сторона: абонент платит, а в сети у него неправильная скорость — это будущая жалоба и уход.
- Руками такую сверку никто не делает.

## Что делает
Ищет 10 типов расхождений:

| № | Расхождение | Чем грозит |
|---|---|---|
| 1 | Сессия в RADIUS есть, договора/услуги в биллинге нет | Бесплатный интернет |
| 2 | Абонент заблокирован в биллинге (долг), а сессия активна и не в редиректе | Потеря выручки |
| 3 | Скорость в шейпере/RADIUS-профиле выше тарифа | Потеря выручки |
| 4 | Скорость ниже тарифа | Жалоба, отток |
| 5 | ONU зарегистрирована на OLT, но не привязана ни к одному договору | Самовольное/забытое подключение |
| 6 | Активный договор, но ни одной сессии и ONU оффлайн > 30 дней | «Мёртвая душа» или ушедший абонент, оборудование не возвращено |
| 7 | Договор расторгнут, ONU/порт ещё активны | Бесплатный интернет, невозвращённое оборудование |
| 8 | Трафик на порту коммутатора, за которым нет договора | Самовольное подключение |
| 9 | Один логин — несколько одновременных сессий с разных мест | Передача логина |
| 10 | Статический IP выдан в сети, но услуга не оплачивается (или наоборот) | Потеря выручки / жалоба |

Для каждого найденного случая:
- сумма потерь в месяц (по тарифу);
- предложенное действие (заблокировать, исправить профиль, привязать, расторгнуть, забрать оборудование);
- после подтверждения — исправление в сети или биллинге через коннекторы (или задача, если автоматическое изменение выключено).

## Кто пользуется
| Роль | Что видит / делает |
|---|---|
| Руководитель | Сумма потерь в месяц, динамика, сколько возвращено |
| Биллинг-администратор | Очередь расхождений, исправления |
| NOC-инженер | Технические расхождения (профили, ONU, порты) |
| Монтажник | Задачи «отключить/забрать» по адресам |

Абонент не участвует.

## Как работает
```
Каждый час (тяжёлые проверки — раз в сутки ночью)
  биллинг      → договоры, услуги, статусы, тарифы (скорости), статические IP, логины
  RADIUS       → активные сессии (логин, IP, MAC, NAS, профиль/скорость, атрибуты)
  BRAS/шейпер  → фактические профили скорости по IP/сессии
  OLT          → зарегистрированные ONU (serial/MAC, порт, статус)
  коммутаторы  → MAC за портами (FDB), трафик на портах
  graph        → привязки договор ↔ ONU ↔ порт

Сверка
  → объединение по ключам: логин, IP, MAC, serial ONU, порт
  → правила 1–10 → случаи с суммой потерь
  → дедупликация: один случай на объект, обновляется, пока не закрыт

Исправление
  → режим "только отчёт" (по умолчанию первые 2 недели)
  → затем: безопасные исправления автоматически (профиль скорости = тарифу, CoA при долге)
           остальное — по кнопке после проверки
  → контрольная сверка через час: расхождение исчезло?
```

## Модель данных
```sql
CREATE TABLE recon_case (
  id            BIGSERIAL PRIMARY KEY,
  rule          SMALLINT NOT NULL,          -- 1..10
  object_kind   TEXT NOT NULL,              -- session, onu, port, contract, ip
  object_ref    TEXT NOT NULL,              -- логин / serial / порт / договор
  contract_id   TEXT,
  details       JSONB NOT NULL,             -- что в биллинге, что в сети
  loss_month    NUMERIC(10,2),              -- потери в месяц, ₽
  suggested     TEXT NOT NULL,              -- block, fix_profile, bind, terminate, collect_device, investigate
  auto_fixable  BOOLEAN NOT NULL,
  status        TEXT NOT NULL,              -- open, fixing, fixed, ignored, false_positive
  first_seen    TIMESTAMPTZ NOT NULL,
  last_seen     TIMESTAMPTZ NOT NULL,
  fixed_at      TIMESTAMPTZ,
  fixed_by      TEXT,                       -- auto / user id
  UNIQUE (rule, object_ref)
);

CREATE TABLE recon_whitelist (              -- служебные подключения, которые не нужно трогать
  object_ref TEXT PRIMARY KEY,
  reason     TEXT NOT NULL,
  until      DATE
);
```

## Правила
- Служебные подключения (офис, узлы, камеры провайдера, тестовые) вносятся в белый список с причиной и сроком.
- Автоматически исправляются только случаи 2 (CoA-блокировка при долге) и 3/4 (профиль скорости приводится к тарифу); остальное — человек.
- Перед массовым исправлением (> 20 случаев за раз) — подтверждение руководителем.
- Случай 6 (мёртвые души) передаётся в модуль 09 (вернуть оборудование) и в биллинг (расторгнуть по регламенту).

## Интерфейсы
- **Сводка:** «Потери: 184 300 ₽/мес; найдено 212 случаев; исправлено за неделю 61 (на 71 800 ₽/мес)».
- **Очередь случаев** по правилам, сумме, району; карточка «в биллинге / в сети» рядом.
- **Кнопки:** «исправить», «в белый список», «ложное».
- **Еженедельный отчёт** руководителю.

## Интеграции
Биллинг (чтение; запись — по включённым действиям), RADIUS (сессии, CoA), BRAS/шейпер, OLT, коммутаторы, `graph`, `tasks`, модули 06 (карточка абонента), 09 (возврат оборудования).

## Метрики успеха
- Сумма потерь в месяц (снижение) и возвращённая выручка.
- Время жизни расхождения (от появления до исправления).
- Доля случаев, исправленных автоматически.

## Риски
- Неверное сопоставление (разные форматы MAC/логинов) даёт ложные случаи → нормализация ключей и режим «только отчёт» в начале.
- Ошибочная блокировка абонента — недопустима: автоматическая блокировка только при подтверждённом долге в биллинге и с журналом.

## MVP (1 неделя)
Правила 1, 2, 3, 5, 7 по выгрузкам биллинга и RADIUS + OLT → отчёт с суммой потерь. Этого обычно достаточно, чтобы окупить всю платформу.

## Как проверить
1. В симуляторе сессия с логином, которого нет в биллинге → случай правила 1 с суммой.
2. Абонент с долгом и активной сессией → случай 2 → автоматический CoA → через час случай закрыт.
3. Профиль 500 Мбит/с при тарифе 100 → случай 3 → профиль исправлен.
4. Служебный логин в белом списке → случая нет.

## Зависимости
Коннекторы биллинга, RADIUS, BRAS, OLT, коммутаторов; `graph`, `tasks`.
